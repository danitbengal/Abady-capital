# שלב 1 — ליבה מאובטחת למערכת האמיתית

## מה בונים ראשון

המסלול הראשון הוא קטן אך מלא: עובד משרד מזדהה, רואה רק לקוחות מורשים, פותח
תיק הצהרת הון, מעלה מסמך לדלי פרטי ורואה אותו ממתין לסיווג ולאישור. אין בשלב
זה OCR אמיתי, שליחת הודעות, חתימה או הגשה לרשות המסים.

## מה נוסף לקוד

- לקוח Supabase נפרד המשתמש רק ב־`VITE_CAPITAL_SUPABASE_URL` ובמפתח הציבורי.
- שער כניסה ב־`?mode=secure`: התחברות בקוד חד־פעמי במייל, הקמה חד־פעמית של
  משרד ראשון, לקוחות לפי RLS, יצירת לקוח ותיק, העלאת מסמך פרטי והורדה בקישור
  חתום ל־60 שניות. הדגם הרגיל נשאר זמין ללא שינוי.
- מיגרציה אחת תחת `supabase/migrations` שמקימה משרדים, משתמשים ותפקידים,
  לקוחות, הרשאות מפורשות, תיקי הון, מסמכים, שעות עבודה ויומן ביקורת.
- RLS בכל טבלה. מנהל רואה את כל לקוחות המשרד; רואה חשבון, עובד ומבקר רואים
  תיק משויך או תיק שקיבלו במפורש; מנהלת חשבונות רואה רק הרשאה מפורשת.
- דלי `capital-documents` פרטי בלבד, עד 20MB, עם גישה לפי משרד ותיק.
- הערה פנימית למסמך נשמרת במסד אך מוגדרת כנייר עבודה בלבד ואסור לכלול אותה
  בטופס 1219, בחבילת חתימה, בחומר ללקוח או לרשות המסים.
- יומן הביקורת ניתן להוספה ולצפייה לפי הרשאה, ללא מדיניות עדכון או מחיקה.

## סדר ההפעלה

1. מריצים את המיגרציה רק בפרויקט Supabase הנפרד של מערכת ההון.
2. יוצרים משתמש משרד ראשון ב־Authentication ומפעילים את `bootstrap_office`
   פעם אחת מתוך משתמש מחובר.
3. בודקים שני משתמשים ושני לקוחות: משתמש מורשה רואה את התיק והמסמך; משתמש
   ללא הרשאה אינו יכול לקרוא רשומה, להוריד קובץ או לנחש נתיב אחסון.
4. מפעילים MFA לעובדי המשרד לפני הכנסת מידע אמיתי.
5. רק לאחר בדיקות ההרשאה מחברים את מסכי הדגם לקריאה וכתיבה אמיתיות.

### הפעלה ראשונה דרך לוח Supabase

1. פותחים את פרויקט ההון `qpgbdivjfactfzwvakkc` ובוחרים **SQL Editor → New query**.
2. מעתיקים את תוכן `supabase/migrations/20261011193000_secure_core.sql` ומפעילים
   **Run** פעם אחת בפרויקט נקי. הקובץ אינו מיועד להרצה חוזרת אחרי הפעלה מוצלחת.
3. ב־**Authentication → Users → Add user → Create new user** יוצרים משתמש משרד
   ראשון במייל של המנהלת. לא מעבירים את הסיסמה בצ׳אט.
4. מגדירים תבנית קוד לפי [email-code-login-he.md](email-code-login-he.md).
   פותחים את מסך הכניסה `?mode=secure`, נכנסים בקוד שנשלח למייל, וממלאים את
   שם המשרד והשם המלא. היישום מפעיל את `bootstrap_office` מתוך המשתמש המחובר.
5. יוצרים לקוח ניסיון, פותחים תיק ומעלים קובץ ניסיון. אין להכניס מידע אמיתי
   לפני השלמת בדיקות הייצור המפורטות להלן.

## תנאי קבלה לפני מעבר לשלב הבא

- אין שימוש במפתח `service_role` בדפדפן או במאגר.
- אין טבלה ללא RLS ואין דלי מסמכים ציבורי.
- שינוי תאריך הצהרה או הגשה אינו מוחק מסמכים ותוכן תיק.
- אישור מסמך מתועד עם המשתמש והזמן; הצעה אינה משנה סכום לפני אישור.
- הערות פנימיות אינן מופיעות בשום יצוא חיצוני.
- בדיקות הרשאה שליליות עוברות עבור מנהלת חשבונות ומשתמש ממשרד אחר.
- גיבוי ושחזור נבדקו בסביבת בדיקות לפני פיילוט.

המיגרציה היא תשתית לבדיקה ואינה מופעלת אוטומטית על מסד הייצור.

## אימות שבוצע והגבולות שלו

`npm test` מריץ גם את המיגרציה עצמה ב־PostgreSQL באמצעות PGlite, עם חוזי
auth/storage מקומיים לצורך הבדיקה. הבדיקות כוללות הפרדת משרדים, שיוך עובד,
חסימת מנהלת חשבונות ללא הרשאה, הרשאה מפורשת, אחסון פרטי, מניעת שינוי שיוך,
אישור מסמך, ביטול אישור בעקבות תיקון סכום, יומן בלתי ניתן לעריכה ושמירת
מסמכים לאחר שינוי מועד. אלה אינן בדיקות על פרויקט Supabase המרוחק.

טרם הושלמו MFA, סריקת קבצים, שחזור גיבוי, חישובים ושיוך אמיתי של מסמך
לשורות הצהרה, הזמנת עובדים ופורטל לקוח. משתמשים כרגע בנתוני ניסיון בלבד.
